# v0.2.7: early launcher exit and trustworthy evidence

## What the Pad screenshots establish

All five supplied screenshots were read. `st-4.jpg` selects the exact selftest
log `arch-session-UAoJTo3F.log`: `selftest=1` at 15:16:52Z, container entry,
start-hyprland, Welcome, then `registration-failed exit=1` at 15:16:53Z.
`st-1.jpg` instead selects the newest log: `selftest=0` at 15:16:55Z and failure
at 15:16:56Z. Restoring weston.service creates that second attempt. Both fail
early; neither screenshot establishes a 30-second selftest gate timeout.

The precise v0.2.6 condition is in
[`host/bin/hypr-session:226–231`](https://github.com/rwanglq-ctrl/omarchy-xiaomipad9pm/blob/566389a/host/bin/hypr-session#L226):
the background launcher no longer exists, `wait` reaps it, status zero is
converted to failure one, and `registered=0` selects `registration-failed`.
The flag only means no Leader query returned a numeric PID greater than one
([lines 205–212](https://github.com/rwanglq-ctrl/omarchy-xiaomipad9pm/blob/566389a/host/bin/hypr-session#L205)).
It is not a machined error, and `exit=1` does not distinguish raw status zero
from one. A live child continues through missing Leader observations until
readiness or the deadline. Adding a registration sleep cannot revive this
already-exited launcher.

`arch-selftest` has no separate registration gate: it invokes `hypr-session
--selftest` with a 90-second outer timeout
([v0.2.6 line 50](https://github.com/rwanglq-ctrl/omarchy-xiaomipad9pm/blob/566389a/host/bin/arch-selftest#L50)).
The Welcome banner establishes that the compositor started executing, not that
it reached output readiness or remained alive. A short-lived registration can
begin and end between the gate's observations. This is reproduced deterministically
with launcher statuses zero, one and seven. Confidence in the early-exit and
misclassification diagnosis is high; the compositor/watchdog's underlying
reason for exiting on this physical Pad remains unproven without the unfiltered
failure and crash-log contents. This release fixes classification and evidence
collection; it does not claim a verified physical-Pad graphics fix.

The dead PID 480 message is emitted only after acquiring the kernel flock
([v0.2.6 lines 122–133](https://github.com/rwanglq-ctrl/omarchy-xiaomipad9pm/blob/566389a/host/bin/hypr-session#L122)).
It is stale file metadata, not a live lock or a failed registration. The owner
token is rewritten before launch. No screenshot establishes a stale-owner cause.

## Why later lines are not a later live probe loop

`finish` prints the failure stage before collecting diagnostics
([v0.2.6 lines 179–180](https://github.com/rwanglq-ctrl/omarchy-xiaomipad9pm/blob/566389a/host/bin/hypr-session#L179)).
The collector reads surviving runtime logs, embeds previous attempt tails and
boot journals ([v0.2.6 arch-diag:20–21,52–64](https://github.com/rwanglq-ctrl/omarchy-xiaomipad9pm/blob/566389a/host/bin/arch-diag#L20)).
Aquamarine's Virtual-1…11 enumeration after the failure marker is copied log
content. Its position in the combined report does not date those events.

The screenshot's `nsenter -t 2169 -a … Virtual-1` commands match the older probe
implementation. v0.2.6 uses `-m -p -r -w --`
([arch-output:42](https://github.com/rwanglq-ctrl/omarchy-xiaomipad9pm/blob/566389a/host/bin/arch-output#L42)).
`Virtual-1` is an autodetected sorting preference, not a required monitor.
The long probe sequence is historical evidence in the collected journal, not
proof that the one-second attempt continued probing. A partially updated
installation cannot be excluded from photographs alone; new per-attempt hashes
make that check possible. These commands are not evidence of the failure's cause.

The missing `arch-hyprland: software=1 no_modifiers=1 no_atomic=0` message is also
explained by source history: v0.2.6 removed it globally when replacing forced
renderer defaults with opt-in settings. The selftest uses the same launcher as
normal sessions. The older messages in `st-4/5.jpg` are inside earlier attempt
and journal sections; absence of that message is not evidence of a skipped
selftest setup path.

  as test failure. Record the first observed Leader separately.

  renderer overrides (`auto` means unset), selected Mesa, watchdog and parent mask.

  prefix journal lines `history:`, and list earlier

  choices and script identity; newer restoration logs; historical journal

  ownership, signals, cleanup, fallback, IPC, CN and Gitee checks remain required.

## Pad update and evidence

Run on the Debian host, from the Linux Terminal text tab or independent SSH.
Updating reuses the existing container. Selftest closes graphical applications
and restores the selected desktop afterward.

```bash
curl -fsSL https://raw.githubusercontent.com/rwanglq-ctrl/omarchy-xiaomipad9pm/v0.2.7/install.sh | OMARCHY_ALARM_REF=v0.2.7 bash -s -- --profile core
export PATH="$HOME/.local/bin:$PATH"
~/.local/bin/hypr-switch arch
log=$(~/.local/bin/arch-selftest); rc=$?
printf 'selftest exit=%s; log=%s\n' "$rc" "$log"
[ -z "$log" ] || less "$log"
```

Inspect the exact printed log, including the crash reports and runtime log
sections; do not select `ls -t … | head -1`. A zero result proves output IPC
readiness and cleanup, not visible physical-Pad frames. Keep private logs intact
and inspect them before sharing. Gold `pad-arch` is read-only and does not
contain the failing device's selftest log. This release pushes origin only.
