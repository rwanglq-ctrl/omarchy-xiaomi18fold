# v0.2.8: truncated staged libLLVM (physical Pad root cause)

This is the first release diagnosed and verified on the failing Pad itself
(Debian host `debian`, kernel `6.12.93-android16`). The gold Pad was used only
read-only, as a reference. Earlier releases were validated in VMs only.

## Evidence on the failing Pad

Read-only collection came first, before any change. The Pad was still on
v0.2.6, because v0.2.7 had never been installed.

- `start-hyprland` printed `Couldn't waitpid for hyprland: No child processes`
  and then `Hyprland exit cleanly.` about one second after Welcome.
- Its wait loop (`start/src/core/Instance.cpp`, 0.56.2) breaks only on
  `WIFEXITED`. A child killed by a signal is reaped first; the next `waitpid`
  then fails with ECHILD. So these two lines mean a **signal death**, not a
  clean exit.
- The unfiltered `hyprland.log` showed the seat opening, `card0` (virtio_gpu)
  and 16 CRTCs. It stopped mid-line while scanning connectors. Hyprland writes
  this log through a buffered `std::ofstream`, so the cut is not the point of
  death.
- There was no crash report. Hyprland installs handlers only for SIGSEGV and
  SIGABRT. The scope peaked at 76.6 MB, with no OOM.
- `/opt/debian-mesa/lib/libLLVM.so.19.1` in the rootfs was **109,051,904
  bytes (exactly 104 MiB)**. The host file is 123,242,120 bytes. The manifest
  recorded the host hash (`deedb2…`), but the copy hashed `5c92dd…`. The other
  seven staged files matched.
- `chroot rootfs python3 -c 'ctypes.CDLL(staged libLLVM)'` died with
  **Bus error (exit 135)**. Mesa's GBM/gallium driver loads this library while
  Aquamarine creates its allocator.

## Exact failure point

1. Aquamarine creates the GBM allocator.
2. Debian `dri_gbm.so` / `libgallium` map the truncated `libLLVM.so.19.1`.
3. Touching a page past the end of the file raises SIGBUS.
4. Hyprland has no SIGBUS handler, so it writes no crash report and loses its
   buffered log.
5. `start-hyprland` reports "exit cleanly" and returns 0.
6. The session turns that into `exit=1`, and the display falls back to Weston.

The copy came from the Oct 14 v0.2.6 install. A fresh `shutil.copyfile` on
the same Pad is correct (four out of four tries, on tmpfs and on the rootfs).
v0.2.6 never fsynced or verified the copy before activating it. The most likely
cause is that the Android Terminal VM stopped before ext4 writeback finished.
This is inferred, not observed.

## A/B on the Pad (one variable per run, `arch-selftest`)

| Run | Change | Result |
| --- | --- | --- |
| A | none (v0.2.6, truncated staged LLVM) | FAIL: ECHILD, `exit=1` |
| B | only `touch ~/.config/arch-use-arch-mesa` | PASS: `output-ready`, `selftest-ready`, rc 0 |
| C | toggle removed; only the cached `libLLVM.so.19.1` replaced by the host file | PASS: `output-ready`, `selftest-ready`, rc 0 |

Debian Mesa itself works. Only the damaged copy fails.

## Why the v0.2.7 upgrade failed on the Pad

v0.2.7 added a hash check for the cached copy and correctly rejected it
(`Mesa hash mismatch`). It never repaired the copy, though, so every reinstall
failed at the same step. The bootstrap then printed `tmp: unbound variable`:
its EXIT trap read a `local` that had already gone out of scope. That hid the
inner status and leaked the checkout.

## Changes

- `lib/debian-mesa.py`:
  - fsyncs each copied library, the manifest, the vendor JSON and the
    directories;
  - verifies the stage before publishing it;
  - never repairs a cached copy in place: when a copy is damaged (libraries,
    manifest or EGL vendor file), it publishes a new generation
    (`debian-mesa-<digest>-N`), switches `/opt/debian-mesa` with an atomic
    `os.replace`, and only then removes the damaged generations;
  - removes temporaries left by a killed install.
- New launcher `arch-mesa-check --verify`. Exit codes: 0 intact, 10 damaged,
  11 operator-owned, 12 absent. Python's own exit codes 1 and 2 count as
  "unverified".
- `arch-hyprland` verifies the staged Mesa on every launch (about 0.3 s on the
  Pad). If the copy is damaged or cannot be verified, it uses Arch Mesa and logs
  `stage=debian-mesa-damaged` or `stage=debian-mesa-unverified`.
- `arch-diag` starts with a `hyprland-signal-death` explanation whenever the
  ECHILD line is present, followed by the Mesa integrity result.
- `install.sh`: the bootstrap checkout variable is no longer function-local.
  The inner status (for example 3) is kept, and the checkout is removed.

## Regression tests

- `mesa-regressions`:
  - a truncated libLLVM, a damaged or missing vendor JSON and a missing
    manifest each produce a new verified generation;
  - a SIGKILL at copy, rename, symlink switch or cleanup always leaves the link
    on a whole copy, and the next install converges;
  - a short copy during staging is never published;
  - fsync covers every library and both JSON files;
  - `--verify` returns 0, 10, 11 and 12.
- `session-regressions`: a manifest mismatch and a missing verifier both lead
  to Arch Mesa with a stage line, and an intact manifest keeps Debian Mesa.
- `display-regressions`: the signal-death hint and the Mesa line come first,
  including in a manual `arch-diag` run.
- `bootstrap-regressions`: a failing inner installer keeps status 3, prints no
  unbound variable and leaks no checkout. This test fails on v0.2.7.
- All earlier regression suites still pass.

## Pad verification of the release tree

- **Installation.** The release tree was installed on the failing Pad
  (`MIRROR=cn`, `--profile core`). The damaged libLLVM was put back into the
  cache first. The installer printed `Replacing damaged cached Mesa copy`,
  activated `debian-mesa-<digest>-2` and exited 0. `arch-mesa-check --verify`
  then reported `intact`.
- **Selftest.** `arch-selftest` reached `mesa=debian`, `output-ready` and
  `selftest-ready`, with rc 0.
- **Launch guard.** With the damaged libLLVM put back into the active copy, the
  launch logged `stage=debian-mesa-damaged` and `mesa=arch-fallback`, reached
  `output-ready` and returned rc 0. Running the Mesa staging step alone then
  repaired the copy.
- **Real path.** `echo arch > ~/.config/hypr-session-mode`, then
  `systemctl --user restart weston.socket weston.service`. The service session
  (`selftest=0`) reached `output-ready` within 2 s.
- **Visible desktop.** `grim` inside the session captured the Omarchy wallpaper
  and bar on `Virtual-1` at 1280×720. In DRM debugfs, `crtc-0` is active and the
  plane framebuffer is allocated by Hyprland at 1280×720.
- **Limit.** The output is the 1280×720 placeholder connector that crosvm
  presents first. This release does not change resizing when the Android
  window changes.
